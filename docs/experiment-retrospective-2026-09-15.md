記録日: 2026-09-15。Phase 1、Phase 2、Lead自動委譲の追加検証を含む。

## 1. 結論と終了判断

**利用者の判断により、本検証は失敗として終了する。安全かつ実用的な自動オフロードの成立は確認できなかった。** 修正・追加実験・ホスト設定・mergeには進まない。

一方、「ローカルLLMが何も実行できなかった」という結果ではない。既存モデルを使い、限定した一時リポジトリで生成・テスト・commit・pushまで到達した。しかし、それは安全性、一般的なタスクへの適用性、ホスト統合、トークン削減を証明しない。独立レビューでは48件すべて成功した状態でも `REQUEST_CHANGES` となった。

今回の失敗は、**限定条件で動くWorkerを、安心して委譲できる運用システムにする条件を満たせなかったこと**と整理する。以下では実測・コード確認・考察・未確認を区別する。Phaseごとの失敗率やモデル性能を測定した比較実験はなく、それらの数値は推定しない。

## 4. 実際につながった経路と未接続部分

確認した経路は次の通り。

```text
手作成のLOCAL判定JSON
  → 生成CLIによる検証・TASK発行
  → 別途起動したWatcher
  → Ollamaによる変更・テスト・自己修正
  → 一時Git branchへのcommit / ローカルbare repoへのpush
  → READY_FOR_REVIEW
```

`READY_FOR_REVIEW` は最終承認・merge・品質保証ではなく、Leadまたは人間のレビュー待ちである。

確認していない経路は、実ホストでの「普通の自然言語依頼 → Astraの適切な委譲判断 → 自動起動 → 完了時のLead復帰」。生成CLI自体は自然言語の危険性を判断せず、Leadから渡された判定・型・値を検証する。TASK発行はWatcherを起動しない。

| 利用ホスト | 確認範囲と制約 |
|---|---|
| Codex | AGENTS.mdを読む仕組みはあるが、本プロジェクトの委譲E2Eを実ホストで証明したわけではない。指示の読込と安全な実行は別の条件 |
| Astra | Leadとして想定した役割。固有ホストの自動読込・実行フックは未確認。モデル名や役割だけでは起動連携にならない |
| Antigravity | 固有指示の自動読込は未確認。非対応ホストでは指示の手動登録が必要だが、本検証では設定していない |

したがって、自動オフロードと呼べるのは「設定済み環境で、発行済みTASKを起動済みWatcherが処理する限定区間」。ファイル配置だけでホスト非依存の無人委譲が完成したとは言えない。

## 6. なぜ失敗したのか：原因の考察

### 6.1 方針を伝えることと、権限を制限することを混同した

Lead指示に「低リスクだけ」「秘密を読まない」と書いても、それはモデルへの期待であり実行権限の制限ではない。入力のriskフィールドがlowでも、生成Pythonが持つ権限は通常ユーザーのままである。shell=Falseやコマンド名のallowlistはシェル注入対策には役立つが、Python内部の動作を隔離しない。

このため「判断を適切にさせる」層と「判断が誤っても被害を限定する」層の間に空白が残った。無人運用ではこの空白が重大になる。

### 6.2 人間向け文書をセキュリティ上の契約として使った

Markdownは読みやすい反面、箇条書き・改行・正規化によって意味が変わる。生成前の文字列だけを検証し、実際の消費側の解釈と突き合わせなかったことで、許可した「ファイル」が「ディレクトリ」に変わった。Diff Guardがあっても、その基準自体が変われば守れない。

必要だったのはチェック項目の追加だけでなく、入力から実行まで同じ構造・意味を維持する契約だった。

### 6.3 事後検出に、事前防止の役割を期待した

Diff Guardや秘密スキャンは生成結果のレビュー補助になる。しかし、テストコードが実行済みなら領域外操作や通信の副作用は戻せない。RESULTの領域外書込みもGuardより先に起こり得た。防御の位置が副作用より後ろにあったことが問題で、検査を増やすだけでは解消しない。

### 6.4 個別機能はあっても、一つの実行契約になっていなかった

Watcher、手動Runner、生成CLIでlock・状態・復旧の扱いが分かれ、Gitもworking treeとindexを別物として十分扱えていなかった。「正常に一回完走する」経路から、同時実行・再起動・途中失敗まで含めた状態機械への設計が不足したと考える。

これは修正点が一箇所に収まらない理由でもある。H1だけを直してもH3は残り、H4だけを直してもM2の競合が前提を崩す。

### 6.5 テストの合格条件が利用の合格条件より狭かった

48件成功は、そのテストで確認した振る舞いの再現性を示す。しかし当時は、変換後スコープ、RESULTリンク、既存stage、全入口競合、実出力での復旧などが不足していた。状態テストの空文字mockは、実Runnerが返すtruthyなIDLEの不具合を見逃した。

E2Eも手作成LOCAL入力と一時repoの成功例であり、Leadの自然言語判断や敵対的入力への耐性を含まなかった。テスト数ではなく「どの失敗条件を防げたか」を受入条件にする必要があった。

### 6.6 本来の価値を測る前に運用基盤の負担が増えた

トークン削減が目的だったが、Leadによる切り出し、TASK作成、結果確認、復旧、基盤修正を含む総トークン・時間・品質の比較は残っていない。基盤が増えるほど安全性確認と運用負荷も増え、便益を示せないまま検証範囲が広がった、と考えられる。

したがって「ローカルLLMだから失敗」「14Bモデルの能力不足」とは断定できない。モデルのタスク別成功率、別モデル比較、Lead単独との費用比較がなく、今回の具体的な阻害要因は実行境界と統合・検証設計だった。

## 7. 修正途中で停止した状態

ローカルbranch `codex/delegation-review-fixes-20260915` に16ファイル（変更13、新規3）の未commit草稿を保持した。共通パス検証、状態enum、排他、Git保護、構造一致、追加22テスト等を試作したが、完成品として公開しない。

68件にはUnicode、RESULT symlink、Windows junction/reparse point、stage/branch、競合・復旧等の追加確認が含まれ、当該環境でskipは0だった。ただし、これを全プラットフォームやすべての競合への保証とはしない。

**H3の人間承認ゲートは未実装。** 状態名の草稿があることと実際に生成コードの自動実行を止めることは違う。修正草稿の実Ollama E2E、最終lint/構文/差分の一括確認、文書更新、最終レビューも完了していない。元の48件に追加22件を足した「70件成功」とは報告できない。

同じOSユーザー権限のAIと人間をローカルの対話CLIだけで完全識別することもできない。対話確認は誤操作を減らすが、同一権限による承認偽装まで防ぐ境界ではない。この承認設計は未確定のまま終了した。

この報告branchでは文書だけをcommitする。未完成修正のcommit/push/stacked PR、merge、利用ホスト設定は行わない。既存の実行コードは修正済みにはなっていないため、無人利用を推奨しない。

## 8. 得られた知見と次回の検証案

以下は将来の提案であり、今回実行する工程ではない。

1. **最初に価値仮説を固定する。** 同じ小規模タスク集合でLead単独とローカル補助を比較し、合格条件・打切り条件を先に決める。計測には上位モデルの総トークン、経過時間、人間の確認時間、修正回数、最終品質を含める。
2. **最初は提案のみ返す。** 信頼できる入力から要約・説明・差分案を作る限定試験にし、生成コードの実行とGit操作を自動化しない。読取り機能にも入力範囲・秘密情報対策が必要で、「read-onlyだから無条件に安全」とはしない。
3. **構造化契約を先に試す。** 実行用データは厳密なschemaと正規化を持たせ、Markdownは表示用にする。実際のparserでの同値性、Unicode、巨大入力、禁止パスを受入試験に含める。
4. **実行を追加するなら境界を先に決める。** 人間承認を運用上の確認とするのか、別権限・隔離で強制するのかを明示する。同一ユーザーで完全防止できると主張しない。TASK IDと差分digestの結合、変更時失効、再起動時の扱いを実装前に決める。
5. **一つの制御経路に揃える。** 全入口が同じlockと状態機械を使う設計で、正常完了より先に停止・timeout・異常終了・競合・復旧を試す。Git試験は一時ローカルbare repoに限定する。
6. **ホスト統合を独立に測る。** 一つのホストに絞り、指示読込の証跡、委譲判断、起動、完了通知をそれぞれ確認する。仕様上読めることと、そのセッションで動いたことを区別する。
7. **進級条件を段階化する。** 提案のみ → 明示レビュー付き変更 → 承認後の隔離実行 → Git連携の順に検証し、前段の価値・安全性が証明できなければ次へ進まない。モデル追加や大規模基盤構築を最初の対策にしない。

再利用候補はTASK/RESULTによる観測しやすい受渡し、安定IDと履歴、既存テスト、一時bare repoのE2E手法、今回見つけた境界条件である。既存実装を安全基盤としてそのまま再利用できるという意味ではない。

## 9. 残る不確実性と終了時の次の工程

- 実務タスク全体の成功率、品質分布、トークン削減率、費用対効果は未測定。
- Astra/Antigravityの自動読込、自然言語からの実ホスト委譲、Lead自動復帰は未確認。
- 悪意ある同一ユーザープロセスとのTOCTOU、完全な秘密情報検出、実行隔離は保証していない。
- 修正草稿の試験成功は、公開済みb86d21dの問題解消を意味しない。

**今回の次の1工程は、この終了報告をGitHubに公開して停止すること。** 次回検証を自動で開始しない。再開する場合は、修正の続きを当然の前提とせず、まず「何を省力化できれば成功か」と「どこまでの権限を許すか」を新しい検証計画で合意する。
